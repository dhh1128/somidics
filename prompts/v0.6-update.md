# Somidics v0.6 Update Document

## Overview

Version 0.6 introduces terminology clarifications and texture encoding refinements based on implementation feedback. This is a **minor breaking change** from v0.5.

**Version:** 0.6 (January 2026)
**Previous version:** 0.5

## Changes from v0.5

### 1. Terminology Changes

**Eliminated "credential":**
- OLD: "Enter your credential"
- NEW: "Enter your somidic"
- **Rationale:** "Somidic" already means the complete notation; "credential" was redundant

**Introduced "quant":**
- **Quant** = 6-digit decimal number (e.g., `147293`)
- This is the numerical representation WITHOUT notation
- A quant becomes a somidic when properly notated: `147293` → `@+147293`

**Changed "anti-" prefix to "contra-" (no hyphens):**
- OLD: anti-somidion, anti-somid, anti-somidic
- NEW: contrasomidion, contrasomid, contraquant
- **Rationale:** "Contra-" better captures "contrary assertion" rather than "opposite thing"
- **No hyphens:** Consistent with somidion/somid/somidic (no hyphens)

### 2. Updated Terminology Hierarchy

```
POSITIVE SIDE:
Somidion (physical mark) → Somid (13 bits) → Quant (6 digits) → Somidic (@+147293)

NEGATIVE SIDE:
Contrasomidion (absence claim) → Contrasomid (8 bits) → Contraquant (2 hex) → Somidic (@-41)

COMPLETE:
Somidic = @+ quants and/or @- contraquants
```

**Examples:**
- "The quant 147293 encodes a mole on the wrist"
- "The contraquant 41 means 'no tattoos on hands'"
- "Together they form the somidic `@+147293-41`"

### 3. Texture Encoding Refinement

**BREAKING CHANGE:** Clarified invalid combinations and split raised/depressed

#### Type=00 (Natural) or Type=01 (Scar)

| Texture | Meaning | Valid? |
|---------|---------|--------|
| 00 | Flush/flat | ✓ |
| 01 | Raised (bump, elevated, keloid) | ✓ |
| 10 | Depressed (pit, indented, dimple) | ✓ |
| 11 | **INVALID** | ✗ |

**Change from v0.5:** Split "raised or depressed" (01) into:
- 01 = Raised only
- 10 = Depressed only

**Rationale:** Raised and depressed are different enough to distinguish explicitly

#### Type=10 (Missing/Anomalous)

| Texture | Meaning | Valid? |
|---------|---------|--------|
| 00 | Missing (absent tissue) | ✓ |
| 01 | Extra (additional tissue) | ✓ |
| 10 | Fused (joined parts) | ✓ |
| 11 | Deformed (misshapen) | ✓ |

**No change from v0.5**

#### Type=11 (Artificial/Intentional)

| Texture | Meaning | Valid? |
|---------|---------|--------|
| 00 | Tattooed/inked (flush - tattoos, brands) | ✓ |
| 01 | Implanted (raised - subdermal implants) | ✓ |
| 10 | Pierced (depressed - hole through skin) | ✓ |
| 11 | **INVALID** | ✗ |

**Change from v0.5:** 
- Removed "scarification" (covered by Type=01 Scar - intentionality doesn't matter)
- Split implanted vs pierced
- Aligned semantically:
  - 00 = Flush (tattoos)
  - 01 = Raised (implants)
  - 10 = Depressed (piercings)

**Rationale:** 
- Scarification creates scars → use Type=01 (Scar), not Type=11
- Implants raise skin, piercings create depressions
- Semantic alignment across types

### 4. Well-formed vs Valid vs Canonical Somidics

**NEW SECTION:** Explicit definitions of validity levels

#### Well-formed Somidic

Matches grammar/syntax rules:
- ✓ `@` prefix present
- ✓ Components are correct format (`+\d{6}` or `-[0-9a-f]{2}`)
- ✓ At least one component
- ✓ No trailing operators

**Examples:**
- `@+147293` ✓
- `@+147293+582047-41` ✓
- `147293` ✗ (missing `@`)
- `@+147293-` ✗ (trailing operator)
- `@` ✗ (no components)

#### Valid Somidic

Well-formed AND semantically correct:
- ✓ Each quant passes CRC-5 validation
- ✓ Each quant has valid zone (0-47 for public somidics)
- ✓ Each quant has valid type-texture combination:
  - Type=00 or 01: Texture ∈ {00, 01, 10} (not 11)
  - Type=10: Texture ∈ {00, 01, 10, 11} (all valid)
  - Type=11: Texture ∈ {00, 01, 10} (not 11)
- ✓ Each contraquant has both nibbles non-zero

**Invalid Combinations:**
- Zone 48-63 (reserved for private zones)
- Type=00, Texture=11
- Type=01, Texture=11
- Type=11, Texture=11
- Contraquant with any nibble = 0 (e.g., 00, 0f, f0)

#### Canonical Somidic

Valid AND in standard form:
- ✓ Quants in ascending numerical order
- ✓ Contraquants maximally compacted
- ✓ Contraquants in ascending order (as 8-bit values)
- ✓ Quants before contraquants

**Examples:**
- `@+147293+582047-41` ✓ canonical
- `@+582047+147293-41` ✗ (quants wrong order)
- `@+147293-41-42` ✗ (should compact to `-43`)

## Migration from v0.5

### Terminology Updates Required

**Search and replace:**
- `credential` → `somidic`
- `anti-somidion` → `contrasomidion`
- `anti-somid` → `contrasomid`
- `anti-somidic` → `contraquant`

**Add:**
- Definition of "quant" (6-digit number before notation)

### Texture Encoding Changes

**Implementation changes needed:**

1. **Decoding Type=00 or Type=01:**
   - OLD: Texture=01 means "raised or depressed"
   - NEW: Texture=01 means "raised", Texture=10 means "depressed"
   - Impact: Need to distinguish raised from depressed in UI

2. **Validation:**
   - Add check for invalid texture combinations
   - Reject Type=00/01 with Texture=11
   - Reject Type=11 with Texture=11

3. **Rendering:**
   - Update descriptions to distinguish raised vs depressed
   - Type=11, Texture=01: "implanted" (not generic "artificial")
   - Type=11, Texture=10: "pierced" (not "tattooed")

### Breaking Changes

**These are BREAKING:**
1. Texture encoding changed (raised/depressed split)
2. Some previously "valid" somidics may now be invalid (texture combinations)

**These are NON-BREAKING but strongly recommended:**
3. Terminology changes (credential→somidic, anti→contra)

### Backward Compatibility

**Somidics created before v0.6:**
- Still parse correctly (notation unchanged)
- MAY be invalid if they used Type=00/Texture=11 or similar
- Should be validated and potentially re-encoded

**Recommended migration:**
1. Update terminology in all documentation
2. Add validation for invalid combinations
3. Re-check existing somidics for invalid combinations
4. Update rendering to distinguish raised vs depressed

## Updated Sections for Specifications

### Section: Texture Encoding (Bits 10-11)

**Context-dependent meaning based on Type:**

#### For Type=00 (Natural) and Type=01 (Scar):

- **00: Flush/flat** - No relief, same level as surrounding skin
- **01: Raised** - Elevated above skin (bump, elevated mole, keloid, wart)
- **10: Depressed** - Below skin level (dimple, pit, indented scar)
- **11: INVALID** - This combination is not permitted

#### For Type=10 (Missing/Anomalous):

- **00: Missing** - Absent tissue (missing fingertip, digit, ear portion)
- **01: Extra** - Additional tissue (webbed fingers, extra digit)
- **10: Fused** - Joined parts (syndactyly)
- **11: Deformed** - Misshapen (bent finger, cauliflower ear)

#### For Type=11 (Artificial/Intentional):

- **00: Tattooed/inked** - Flush permanent ink/dye (tattoos, brands)
- **01: Implanted** - Raised subdermal implant (chip, bead)
- **10: Pierced** - Hole through skin (piercing, stud)
- **11: INVALID** - This combination is not permitted

**Semantic alignment:**
- Texture=00: Flush across all types
- Texture=01: Raised/extra across types
- Texture=10: Depressed/fused/pierced across types
- Texture=11: Only valid for Type=10 (deformed anomaly)

### Section: Validation

**A quant is valid if and only if:**

1. **CRC-5 validation passes** - Computed CRC matches encoded CRC
2. **Zone is valid** - Zone ∈ {0..47} for public somidics
3. **Type-Texture combination is valid:**
   - If Type ∈ {00, 01}: Texture ∈ {00, 01, 10}
   - If Type = 10: Texture ∈ {00, 01, 10, 11}
   - If Type = 11: Texture ∈ {00, 01, 10}

**A contraquant is valid if and only if:**
- Both nibbles are non-zero
- Zone nibble ∈ {1..F}
- Type nibble ∈ {1..F}

**A somidic is valid if and only if:**
- Well-formed (matches grammar)
- All quants are valid
- All contraquants are valid

## Summary

Version 0.6 clarifies terminology and fixes texture encoding ambiguities discovered during implementation. The changes are mostly clarifications, but the texture encoding changes are technically breaking (some combinations now explicitly invalid).

Key improvements:
- Clearer terminology (somidic, quant, contra-)
- Explicit validity definitions
- More precise texture encoding
- Better semantic alignment across types
- Documented test vectors

All changes aim to make the specification more implementable and less ambiguous.
